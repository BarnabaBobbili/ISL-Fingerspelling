Training and calibration

python src/static/train_v2.py --tag main                        # final model
python src/static/train_v2.py --tag xsrc --holdout isl_data     # cross-dataset experiment

Data​

PoolContentRole
train_staticStatic Datasets A, B and C, original train splitbulk of the data
train_realaligned real-video letters from training videostarget domain, sampled 4× more often
val_realaligned letters from validation videosmodel selection and calibration
test_realaligned letters from test videosfinal test

Model selection uses validation real-video accuracy, never the near-duplicate static validation set (that one saturates at 98 % and would select an over-fitted model).

Sampling​

Each step draws 256 samples with replacement, weighted by domain weight / √(class frequency in that domain), so rare letters are not drowned and the real-video domain makes up ≈ 69 % of the sampling mass.

Optimisation​

AdamW (lr 2·10⁻³, weight decay 10⁻²), one-cycle schedule, label smoothing 0.05, gradient clipping 1.0, EMA of the weights (decay 0.998; the EMA model is what is evaluated and saved), 30 epochs × 32,000 samples, early stopping (patience 8) on validation real-video accuracy. About 20 minutes on a laptop CPU.

Calibration​

Raw soft-max scores are rarely trustworthy. After training, a single temperature T is fitted on the validation real-video logits by minimising negative log-likelihood (L-BFGS); the deployed confidence is softmax(logits / T) with T ≈ 0.84 stored in the checkpoint. The expected calibration error (ECE) on real test videos fell from 0.17 (baseline) to 0.011 (proposed model): a displayed 96 % really means about 96 %.

Calibration does not transfer to new setups

On a completely unseen dataset (Static Dataset B, excluded from training) the model is over-confident: ECE 0.08 uncalibrated, 0.13 after the real-video temperature (0.14 → 0.18 without second-hand recovery). Confidence is only as good as the match between the live camera and the training domain — see Limitations.

Second-hand recovery​

Every image was re-extracted with second-hand recovery and the model retrained (--tag main_r, --tag xsrc_r). Compared with the same training on plain landmarks:

plain landmarkswith recovery
real-video test accuracy95.7 %95.9 %
expected calibration error (real, calibrated)0.0150.011
cross-dataset accuracy on Static Dataset B64.0 %70.0 %

The cross-dataset gain (+6 points) was decisive: the application's static classifier is the recovery model (checkpoints/dh_gat_v2_main_r.pt) and the static tracker runs with recovery on (HandTracker(recover=True)). Checkpoint names ending in _r select this automatically. The continuous model keeps the plain tracker, because its features were computed without recovery.

A side effect is that recovery sometimes adds a spurious second hand to one-handed letters (about 18 % for O). The classifier tolerates it, and the hold detector ignores the brief prediction flicker it can cause (see Hold detection).

Effect of stronger augmentation​

The cross-dataset gap appeared to be a camera-viewpoint and depth problem (MediaPipe's depth estimate differs from camera to camera), so train_v2.py --strong-aug widened the 3D rotations (±35°), added random per-hand depth scaling (0.5 – 1.6×), larger per-hand rotation (±20°) and more hand dropout (8 %). Trained without Static Dataset B and tested on it, it performed worse:

adopted recipestrong augmentation
cross-dataset accuracy (Static Dataset B unseen)70.0 %65.5 %
real-video test95.5 %95.3 %
original in-domain test97.8 %97.8 %

Distorting the geometry more strongly therefore does not close the gap; it removes information the classifier relies on. The stronger recipe was not adopted (the flag is kept so that the experiment can be reproduced). Improving the input, through second-hand recovery, gave +6 points. Data from the target camera is expected to help most: recordings made with src/static/collect_webcam_data.py can be used for fine-tuning.
