Design decisions

The significant design choices, with the reason for each and the alternative that was rejected.

Data and baseline models​

IDDecisionWhyRejected alternative
DD-001CTC vocabulary = 26 lower-case letters, blank = 26digits/symbols in the transcripts are annotation artefacts with near-zero frequencykeep all 38 characters
DD-002Use the authors' video-level train/test split; hold out 10 % of training videos for validationavoids segments of one video in two splits; comparable with the paperrandom segment-level split (leakage between segments of the same video)
DD-003Missing landmarks: forward-fill ≤ 5 frames, then zero-fill; drop segments with > 50 % missingbrief occlusions should not create jumps to the originzero-fill everything
DD-004Cache landmarks as .npy per segmentmemory-mapped, no extra dependencyHDF5
DD-005Normalise: wrist → origin, scale by wrist → middle-MCP distancewrist is the most stable joint; scale is robust to hand orientationimage-frame coordinates
DD-006BiLSTM-CTC baseline (Linear → 2 × BiLSTM(256) → CTC)standard strong baseline, future context helps co-articulationuni-directional LSTM
DD-007Conformer-CTC main model (d = 144, 4 blocks)convolution for local handshape patterns, attention for global contextpure Transformer (no local bias)

Recognition, live decoding and 3D hands​

IDDecisionWhyRejected alternative
DD-008Report three static tests (in-domain, cross-dataset, real video)a random split of near-duplicate frames gave 98 % while accuracy on real frames was 38 %single random split
DD-009Build real frames with CTC forced alignmenteven time division mislabels frames; alignment gives true letter timingmanual labelling (too slow), even split
DD-010Shared-frame two-hand graph with cross-hand attentionmost ISL letters are defined by contact between the handsper-hand normalisation (information loss)
DD-011Slot hands by wrist-x, mirror-augmentMediaPipe's Left/Right label flips between mirrored and normal videouse the handedness label
DD-012Temperature scaling on real-video validation logitsone parameter, preserves accuracy, large ECE gainno calibration; Platt/isotonic (more parameters than needed)
DD-013Model selection by real-video validation accuracystatic validation saturates at 98 % (near-duplicates)static validation accuracy
DD-014Second-hand recovery with the same 0.4 thresholdrecovers J/S/B hands with ≤ 2 % false hands on one-handed lettersextra pass at threshold 0.15 (hallucinated hands: I 20 %, O 48 %)
DD-015Continuous input = trunk embedding + posteriors + raw geometry + motionpretrained hand-shape knowledge plus a path independent of the trunklandmarks only (baseline)
DD-016Ablation without trunk features (--parts raw)shows what pre-training contributesassume it helps
DD-017Smaller convolution kernel (15) and an intermediate CTC loss~0.5 s per letter at 30 fps; auxiliary loss regularises small datakernel 31, single loss
DD-018Hold detector: motion-still + stable arg-max + re-armingper-frame guesses include transitions; repeats need a releasecommit on every confident frame
DD-019Letter poses = medoid of real samples, not hand-modelledthe 3D hands sign exactly what the recogniser knowsmanually posed hands
DD-020Contact discovery in the image plane; depth registration before alignmentMediaPipe z is relative to each wristfull 3D distances (polluted by unobservable depth offset)
DD-021Kabsch rigid alignment (clamped to 20°) + FABRIKrigid body keeps the hand shape; IK resolves competing contactsper-joint snapping (distorts the hand)
DD-022Server on Starlette, WebSocket pull-based framesFastAPI/Starlette version conflict on the target machine; one frame in flight bounds latencyFastAPI; push-based streaming (queueing)
DD-023HUD drawn client-side on a canvaszero extra latency, identical look for webcam and uploaded videoserver-side annotated frames only
DD-024Three.js vendored locallyworks offlineCDN
DD-025Track hands in the browser and send landmarks, not picturesremoves JPEG encoding and server-side detection from the live critical path (the server tracker managed ≈10 fps), and no frame leaves the pageserver-side tracking only (kept as automatic fallback)
DD-026Resample to a fixed 30 Hz grid before the live modelthe models were trained at 30 fps; slow cameras then cost little (10 fps camera: 5.7 % vs 13 % error)feed frames as they arrive
DD-027Stable-prefix commit with a greyed tentative tailcommitted letters never change; the delay is bounded (≈0.4 s)re-decode and replace the whole text each time (flicker)
DD-028Hold detector in seconds, not framesidentical behaviour at 15, 30 and 60 fpsframe-count thresholds
DD-029Train for live use: sub-word crops, speed 0.55–1.3×, word joinswindows start mid-word and people sign faster live; error at 2× speed 11.6 % → 5.8 %whole-word training only
DD-030Hands = skinned mesh retargeted from landmarks, flat-skeleton awarereal hand shapes; the model's skeleton is flat, so rotations are carried along chains explicitlycylinders and spheres (rubbery), or per-bone shortest arc (flips near 180°)
DD-031Pick the left- or right-hand mesh from each pose's real geometry; never mirror a poseevery letter keeps the shape and orientation in the data (forcing a fixed handedness by mirroring changed some signs)mirror a hand across its palm plane
DD-032A hand that is not needed waits below the frame and rises when neededno floating second hand; natural entry and exitdraw a faded second hand
DD-033Documentation built into the app (Docusaurus at /docs, embedded under the site header)one place to read and use the project; same fonts and palette, synced themea separate docs site
DD-034Hands and sleeves only, no head or bodya body model with inverse-kinematics arms looked unnatural and bent the arms awkwardly; the hands need to be large and in the orientation given by the dataupper-body figure (built and dropped)
